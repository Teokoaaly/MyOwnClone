# Thread — Arquitectura real de MyOwnClone

Qué hace el producto por dentro, verificado contra bundles y código. Este thread es el contrapeso de [[myownclone-strategy-and-vision]]: allí está lo que el founder quiere que sea; aquí está lo que el código hace. La distancia entre ambos threads es, en gran parte, el backlog del producto.

> **⚠️ Actualizado 2026-10-22 — este thread describe la generación anterior del despliegue.**
> La re-verificación en vivo (`0-raw/2026-10-22-myownclone-live-reverification.md`) encuentra que el sitio ya no está en Vercel, ya no tiene nueve subdominios, ya no expone cero endpoints REST y ya no usa Poppins ni PostHog. Lo que sobrevive intacto es la parte derivada del **checkout local del código** — la arquitectura de dos repos, el drift de schemas, el pipeline de chat — porque esa evidencia no depende del hosting. La parte de **superficie desplegada** (hosting, API, stack, instrumentación, diseño) es histórica. Ver [[myownclone-estado-live-2026-10]].

## La capa de inferencia: entre API propia, gateway y relay

Esta sección añade a lo anterior la pieza que faltaba: **de dónde sale la inferencia y con qué abstracción**. Todo lo de 2026-10-22 describe un producto que consume inferencia como un backend opaco; el material del 2026-10-23 permite ver el **mercado de esa capa** por dentro —el software que la implementa (new-api), el mercado que la revende (los 中转站 de PriceAI) y el patrón que se repite cuando no hay API oficial (midjourney-proxy).

### Lo que hay hoy: un puntero, no una capa

El estado actual es el de un **proveedor único detrás de una variable de entorno**: el `README.md` del repo declara *LLM: DeepSeek (configurable via `OPENAI_API_BASE`)*, y `AGENTS.md` lo repite como dependencia crítica (`OPENAI_API_BASE` — proveedor LLM, DeepSeek por defecto). No hay router, no hay grupos, no hay precios por uso, no hay failover. Encima de ese puntero, Dify actúa como capa de prompts y recuperación ([[2026-1022-gap-dify-como-capa-inferencia-prompts]]), y el consumo se factura al tenant por categorías sobre un desglose **por proveedor** (Anthropic + OpenAI) ([[2026-1022-costes-por-categoria-tenant]]). Los embeddings, en cambio, están partidos: Voyage en el competidor ([[2026-1022-myclone-viaje-embeddings-voyage]]) y `text-embedding-3` inferido aquí ([[2026-1022-pgvector-embeddings-openai-inferidos]]).

Es decir: **la inferencia es una dependencia, no una arquitectura**. Y el propio thread ya sabe que dos de las tres piezas que un producto serio necesita de esa capa —API de consumo y precios públicos— **no existen todavía** (fricciones 3 y 4).

**Corrección de esta tanda (2026-11-03):** el embedding del que el thread da por hecho (`text-embedding-3` sobre PGvector) **no es el que el código ejecuta**. La ruta viva construye un vector de 1.536 dimensiones con un **hash FNV-1a de los términos** y calcula el coseno en Python, sobre un `ARRAY(Float)` de Postgres. La afirmación anterior era una inferencia a partir de Neon, no una verificación; ver «La capa vectorial: lo que el código hace y lo que el compose promete».

### Qué es un gateway: la anatomía de new-api

El caso canónico de esa capa ausente es **New API** (`QuantumNous/new-api`), un gateway de IA autoalojado, fork AGPLv3 de One API (MIT), que se describe como un *"unified AI model hub for aggregation & distribution"* y **convierte varios LLM a formato OpenAI-, Claude- o Gemini-compatible** ([[2026-1023-new-api-gateway-unificado-de-modelos]]). Los upstreams declarados son OpenAI, Anthropic, Gemini, Azure OpenAI, AWS Bedrock, Vertex AI, DeepSeek y Qwen.

Lo que el README documenta, pieza por pieza:

- **Una sola API, varios protocolos** — `/v1/chat/completions`, `/v1/responses`, `/v1/messages`, `/v1beta/models/{model}:generateContent`, más imágenes, audio, `/v1/embeddings`, `/v1/rerank` y plugins de tareas ([[2026-1023-new-api-una-sola-api-multiproto]]). El embedding y el rerank bajo la misma clave es exactamente la pieza que hoy está partida entre Voyage y `text-embedding-3`.
- **Canales, grupos y routing** — un canal es una clave upstream con modelos y **asignación de grupo**; el routing se decide por grupo, prioridad, peso, afinidad y *channel-pin*; la key del cliente debe compartir grupo y modelos con el canal ([[2026-1023-new-api-routing-por-grupo-prioridad-y-afinidad]]). El **grupo** es la palanca comercial: es la unidad a la que se asigna el precio ([[2026-1023-new-api-grupos-como-eje-de-precio-del-relay]]).
- **Dos motores de precio** — precios por *ratio* (倍率) por modelo y por nivel de uso, y un sistema de **expresiones** con precios propios de caché (`cc`, `cc1h`, `cc12h`), pico/valle y precios por número de peticiones ([[2026-1023-new-api-precios-por-ratio-y-expresion]]).
- **Contabilidad de tokens** — `tokenkit` existe porque las estimaciones nativas subcontaban el tráfico de agentes (definiciones de tools, function calls y sus salidas) **31–93 %** frente a 54 ventanas reales de Claude Code y Codex; el arreglo deja ≤1 % de sesgo ([[2026-1023-new-api-tokenkit-conteo-de-tokens-calibrado]]). Es decir: **la normalización por tokens es en sí misma un producto**, con su propio modelo de error.
- **Conversión con pérdida declarada** — `relaykit` es el módulo que convierte entre los cuatro protocolos de texto y el README avisa de que *"protocol-specific tools and fields may not map exactly"* ([[2026-1023-new-api-relaykit-conversion-perdida-de-campos]]). "Compatible con OpenAI" no es "idéntico a OpenAI", y el propio proyecto lo dice.
- **Extensibilidad** — las tareas asíncronas (imagen, vídeo) son **plugins JavaScript en sandbox**; cada plugin valida su request y declara sus propios hechos de uso, y el gateway solo los acota ([[2026-1023-new-api-plugins-de-tareas-js-en-sandbox]]). El soporte de un proveedor no está en el core: cambiar de proveedor en una capacidad no toca el núcleo.
- **Despliegue** — local con un contenedor y SQLite; en producción, `docker-compose.yml` levanta **New API + PostgreSQL + Redis**, con ClickHouse opcional para el log de consumo ([[2026-1023-new-api-despliegue-postgres-redis-y-clickhouse]]). Sobre eso, una advertencia operativa de manual: sin Redis compartido, *"rate limiters count limits independently per node"* ([[2026-1023-new-api-seguridad-env-vars-y-rate-limit-por-nodo]]).
- **Licencia** — AGPLv3 con Sección 7: **enlace visible al proyecto original y aviso de atribución en la interfaz**, visible para el cliente final ([[2026-1023-new-api-licencia-agplv3-y-atribucion-en-ui]]). Choca de frente con una marca propia sin filiación y con la ausencia de código público en el vault.
- **Aviso legal** — el README condiciona explícitamente el uso a claves upstream legítimas, cumplimiento de ToS, y para operación pública: registro, licencias, seguridad de contenido, **verificación de identidad real, retención de logs, impuestos** y autorización upstream ([[2026-1023-new-api-aviso-legal-para-reventa-publica]]).
- **Escala** — 50,5k stars, 6.608 commits, actividad el mismo día de la captura, 7 idiomas en consola; la advertencia operativa es que `latest` se mueve y hay que fijar versión ([[2026-1023-new-api-escala-adopcion-y-traduccion]]).
- **Stack** — monolito **Go + Gin** con el front **React 19 / Rsbuild / Tailwind 4** embebido (`web/dist`), Bun como runner, y un wrapper Electron; el backend es el producto, no una capa aparte ([[2026-1023-new-api-stack-go-gin-react19-y-electron]]).

El dato estructural que cierra el círculo: **Midjourney-Proxy es un upstream declarado de new-api** ("Midjourney interface support"), y a la vez el README de Midjourney-Proxy lista `new-api` entre las aplicaciones que lo consumen ([[2026-1023-midjourney-proxy-ecosistema-de-aplicaciones-que-lo-consumen]]). Dos proyectos que se citan mutuamente y se montan uno sobre otro.

### El mercado: qué se compra cuando no hay contrato

PriceAI es un agregador, no un vendedor: su home se define como *"AI 低价卡网订阅与中转 API 比价雷达"* y su FAQ dice *"PriceAI 不卖货、不收款、不参与交易"* ([[2026-1023-priceai-home-como-radar-y-no-como-vendedor]]). Estructura en cuatro módulos con ejes distintos:

| Módulo | Qué compara | Átomo |
|---|---|---|
| 卡网订阅 | cuentas, membresías, correo, 卡密, CDK, Kiro — precio con stock y modo de entrega | [[2026-1023-priceai-modulo-kanet-marcas-y-modos-de-entrega]] |
| 官方订阅 | precio oficial, precio regional, elegibilidad y umbral de pago | [[2026-1023-priceai-catalogo-ocho-canales-y-fecha-de-tipo-de-cambio]] |
| 官方 API | cuota gratuita, Token Plan y límites de los proveedores chinos | [[2026-1023-priceai-sin-cuotas-gratis-tabuladas]] |
| 中转 API | multiplicador (倍率), estabilidad e información declarada | [[2026-1023-priceai-modulo-api-transit-tres-ejes-de-comparacion]] |

La tabla de reventa usa **fuente de canal** como campo estructural: **22 de las 30 filas son Sub2API y 8 son New API** ([[2026-1023-priceai-transit-canal-tipo-sub2api-vs-new-api]]). Comparar 30 relays es comparar, en su mayor parte, despliegues del mismo stack con distinto 号池 y distinto multiplicador.

El precio se expresa como **综合倍率 = 充值系数 × 模型倍率** ([[2026-1023-priceai-transit-formula-del-multiplicador-compuesto]]) y la dispersión es real: de **0.04x–0.10x** en 悠米AI中转 (New API) y 0.01x–0.20x en 皓悦 APISub2API, hasta **7.00x** en 合聚API para ChatGPT ([[2026-1023-priceai-transit-dispersion-de-multiplicadores]]). Tres límites que el multiplicador no cubre:

- **Cobertura parcial por diseño** — la cabecera declara *"排名只用有直连监测的分组"*: solo entran los grupos con monitorización directa. "No收录" en la columna Gemini (6 filas) y en Claude (3) significa "no observable", no "no existe" ([[2026-1023-priceai-transit-cobertura-parcial-y-criterio-de-ranking]]).
- **El precio no predice la estabilidad** — 悠米AI中转 es el más barato (0.04–0.10x) y tiene 85,1 % de disponibilidad; HubCore llega a 99,8 % con techo de 2,00x; 贝贝 tiene la disponibilidad mínima (73,9 %) con Claude a 0,05–1,60x ([[2026-1023-priceai-transit-precio-y-estabilidad-desacoplados]]). ### El arquetipo: cuando no hay API oficial, alguien construye el puente

`novicezk/midjourney-proxy` (Apache-2.0) **convierte el canal de Discord de Midjourney en una llamada por API** — *"代理 MidJourney 的discord频道，实现api形式调用AI绘图"* ([[2026-1023-midjourney-proxy-convierte-discord-en-api-rest]]). El patrón es exactamente el mismo que el de Dify en este producto: un puente HTTP entre una interfaz que no es API y el consumidor que sí necesita API.

La anatomía del acoplamiento es lo que hay que mirar: el proxy **no se autentica contra Midjourney, sino contra Discord**, con token de usuario, ID de servidor e ID de canal; el WebSocket con token de usuario es lo que da los mensajes de error y la funcionalidad completa ([[2026-1023-midjourney-proxy-arquitectura-token-discord-y-wss]]). De ahí vienen sus dos dinámicas: multi-cuenta con cola por cuenta ([[2026-1023-midjourney-proxy-funcion-multicuenta-con-cola-por-cuenta]]) y riesgo de aviso o baneo por frecuencia de dibujo ([[2026-1023-midjourney-proxy-riesgo-de-cuenta-por-frecuencia-de-dibujo]]). Y sus defaults son la mitad del aviso: `mj.task-store.type` en memoria por defecto (se pierde al reiniciar) y **`mj.api-secret` vacío = autenticación desactivada** ([[2026-1023-midjourney-proxy-config-tareas-y-autenticacion]]).

Aquí está el paralelismo estructural con el bug `myownclone_public_bp`: **un endpoint que debería existir y no existe**. El chat público devuelve 404 porque la ruta no está registrada ([[2026-1022-live-verify-superficie-rest-api-inexistente-antes]]), y en el otro lado del mercado el mismo hueco —proveedor sin API— se llena con un puente no oficial, frágil y con el default abierto. La lección de los dos lados es la misma: **la capa de acceso a inferencia es la decisión de arquitectura que más caro sale cuando se pospone**. Si el proveedor no da API, alguien va a construir el puente; la elección es si lo construyes tú, con su tríada de degradación (cuenta, sesión, rate limit) asumida, o si compras acceso a un puente ajeno.

Y en el ecosistema de estos proxies el valor no está en el proxy: hay siete aplicaciones de terceros construidas encima —integración en otros chats, plataformas de agregación, empaquetado móvil— y también una herramienta para **eludir el captcha del proveedor** ([[2026-1023-midjourney-proxy-ecosistema-de-aplicaciones-que-lo-consumen]]). Es decir: demanda real servida sin SLA y sin superficie legal ([[2026-1023-midjourney-proxy-relevancia-para-clones-con-imagen]]).

### El arquetipo tiene dos ediciones, y eso es el dato de negocio

La edición abierta de `midjourney-proxy` documenta exactamente **siete capacidades** en "主要功能" ([[2026-1023-midjourney-proxy-funciones-imagen-base64-y-describe]]): la instrucción Imagine con sus acciones, **imagen en base64 como垫图 (imagen de referencia)**, **Blend** (mezcla) y **Describe** (imagen a texto), **progreso de tarea en tiempo real**, **traducción de prompt chino→inglés configurable (Baidu Translate o GPT)**, **predetección de palabras sensibles con override manual** y la conexión `user-token` por WSS para obtener errores y funcionalidad completa.

Eso define qué significa "API" para un generador de imágenes: no prompt→PNG, sino **reproducir el vocabulario de botones del bot de Discord**. Pero dos de esas siete funciones no son de imagen sino de producto: la traducción **delega** su trabajo a Baidu o a GPT según `mj.translate-way`, y el filtrado de palabras sensibles es un override manual. Es exactamente el patrón de "capa de inferencia externa" que este producto ya usa con Dify ([[2026-1022-gap-dify-como-capa-inferencia-prompts]]): **el núcleo del proxy no es el modelo, es el orquestador de capacidades ajenas**.

La lectura de negocio está en el reparto entre ediciones. El README de la edición abierta remite a `midjourney-proxy-plus` ([[2026-1023-midjourney-proxy-edicion-plus-ampliada]]), y el reparto es quirúrgico: **todo lo que es "uso del modelo"** (Imagine, Blend, Describe, traducción, sensible) queda en la edición abierta; **todo lo que es "operación sobre el proveedor"** vive en la de pago — pool de cuentas persistente y mantenido dinámicamente, consulta y ajuste de `settings`, **verificación automática de popups**, **apelación automática de "Action needed to continue"**, resolución de caída frecuente de token, panel de administración embebido, configuración dinámica en backend, además de funciones de imagen (Pan, Zoom, Vary, Remix, seed) y generación de vídeo con soporte V7 Alpha.

Es decir: **el core público es "llamar al dibujo por API" y lo premium es "que no te baneen"**. Eso mapea casi exactamente contra el eje del producto propio: el core público es el clon; lo que se cobra aparte es la operación. Es un precedente de pricing del sector que el vault no tenía, y también una advertencia: la edición plus declara perseguir las versiones del proveedor (V7 Alpha, vídeo) mientras la edición abierta tiene **229 commits con el último cambio de código en `src/main` de junio de 2024** — el único movimiento posterior fue el README, en agosto de 2025 ([[2026-1023-midjourney-proxy-popularidad-y-actividad-del-repo]]). La curva es instructiva: **5,4k stars y 2,4k forks, pero el código congelado desde hace más de un año**; la popularidad no se convirtió en mantenimiento porque el esfuerzo se mudó a la edición de pago. Es un precedente de que el propio sector financia la continuidad con una edición separada, no con el código abierto — y el contraste con el producto propio es directo: aquí el código abierto es el activo comercial principal, allí no hay repositorios públicos ([[2026-1022-sin-repos-publicos-github]]).

Y hay una lectura operativa de coste que conecta con el thread de costes: el apartado "快速启动" ofrece **tres vías de despliegue, dos sin servidor propio** — Railway (*"基于Railway平台，不需要自己的服务器"*), con Zeabur como alternativa, y Docker en servidor o local ([[2026-1023-midjourney-proxy-despliegue-java17-y-paas-sin-servidor]]). El stack es **Java 17 + Maven + `application.yml`**, con `ProxyApplication` como entrypoint y `docker build . -t midjourney-proxy`. Es decir: **levantar este puente puede costar 0 € de servidor** si se acepta un PaaS, contra el suelo de €5,99/mes de Hetzner que no cabe en el presupuesto de ≤ €4/mes ([[2026-1023-hetzner-presupuesto-4-euros-no-alcanza]]). Y el stack mainstream es una señal: una integración con un proveedor sin API oficial **no exige un lenguaje exótico** — el trabajo real está en el estado, las cuentas y la resiliencia, no en la implementación. Detalle operativo que importa: la persistencia de tareas en Redis es un requisito adicional que en un PaaS puede implicar un servicio de backing aparte.

### Una tercera edición del arquetipo: el gateway que también fabrica la cuenta

`AuuCoder/gptGrok2api` (285 estrellas, 145 forks, 24 commits, 12 tags, MIT, último release **v1.2.1 del 27 de julio de 2026** — sin actividad desde entonces; [[2026-1024-gptgrok2api-285-estrellas-y-24-commits-con-12-tags-y-3-mes-sin-movimiento]]) es el mismo arquetipo con una diferencia que cambia su naturaleza: **no solo construye el puente, también produce la credencial que lo alimenta**. Su README lo describe como *"ChatGPT/Grok registrador | Grok registrador | registro totalmente automático por protocolo puro"*, y el módulo de gateway **fusiona tres catálogos —GPT, Grok SSO y Grok Build OAuth—** bajo una raíz `/v1` que despacha por modelo, conservando `/grok/v1` como interfaz Grok completa ([[2026-1024-gptgrok2api-gateway-unificado-gpt-y-grok-en-api-compatible]], [[2026-1024-gptgrok2api-compatibilidad-multiprotocolo-y-despacho-por-modelo]]).

Lo relevante para la decisión build-vs-buy no es el puente —eso ya lo sabía el thread— sino **las tres partidas de aprovisionamiento que este proyecto cierra dentro del repo**:

- **Correo**: cinco proveedores integrados (temporal, GPTMail, Outlook Token, Microsoft Alias e iCloud Privacy Mail) y un **sidecar propio de iCloud Privacy Mail** con contrato explícito: **20 buzones/hora** en la interfaz nueva, **5/hora** en la antigua, **25/hora** sumando ambas, y **tope de 750 buzones acumulados por cuenta**, con temporizador de 60 minutos por ronda ([[2026-1024-gptgrok2api-icloud-privacy-mail-fabrica-de-correo-con-techo-decreciente]]). El correo deja de ser un coste por unidad sin techo y pasa a tener **ciclo de vida y rendimiento decreciente por diseño**.

**El correo tiene tres regímenes, y solo uno sirve a un pipeline.** La línea de aprovisionamiento que este repo internaliza —cinco proveedores de correo más el sidecar de iCloud Privacy Mail, con contrato explícito de **20/5/25 buzones por hora** y **tope de 750 acumulados por cuenta** ([[2026-1024-gptgrok2api-icloud-privacy-mail-fabrica-de-correo-con-techo-decreciente]])— es la variante **internalizada** de una partida que el mercado resuelve de tres maneras distintas. La primera es la **función de biblioteca**: el bot de registro genera el buzón con `generator.email`, recoge el OTP solo y el coste marginal del buzón es cero, aunque sea una inferencia de diseño y no un precio medido ([[2026-1024-chatgpt-creator-correo-temporal-y-otp-automatico-con-generator-email]]). La segunda es el **proveedor pago y automatizable**: NotLetters vende por correo a **0.05 ₽** y expone web, HTTP API e IMAP por el 993 con SSL ([[2026-1024-notletters-precio-005-rubles-por-correo-y-contadores-de-escala]], [[2026-1024-notletters-tres-vias-de-consumo-api-http-imap-y-web]]). La tercera es `emailondeck.com`: **"always simple and free"**, dos pasos en el navegador, **ni un precio publicado** —tampoco del plan PRO en `pro.emailondeck.com`— y **ninguna vía de consumo programable** ([[2026-1026-emailondeck-gratis-con-paso-pro-sin-cifras]]).

La lectura para la decisión build-vs-buy es una **columna que hoy no existe en la comparación**: no solo "coste por buzón", sino **"¿la unidad es automatizable?"**. Un buzón gratuito que hay que usar a mano no puede alimentar un pipeline automatizado, de modo que el "gratis" de EmailOnDeck **no baja el coste de esta partida** para el caso de uso del repo ([[2026-1026-emailondeck-casos-de-uso-de-consumo-y-no-de-registro-masivo]]). Y la segunda lección del corpus es que **el contrato explícito del sidecar no es la norma del sector**: un proveedor con 11 años de operación y **"Over 215,158,204 temporary emails processed"** publicados ([[2026-1026-emailondeck-contador-215158204-correos-procesados]]) **no publica ni un plazo de retención, ni un límite de buzón, ni un SLA** ([[2026-1026-emailondeck-captura-minima-344-palabras-y-cero-especificacion-operativa]]). El valor del sidecar como diseño es, por tanto, mayor de lo que sugiere su precio: **el contrato es lo que hay que construir**, y el mercado no lo da por compra.

**El correo tiene cuatro regímenes, y solo uno sirve a un pipeline — y el único que publica contrato es el que no sirve para esto.** La línea de aprovisionamiento que este repo internaliza —cinco proveedores de correo más el sidecar de iCloud Privacy Mail, con contrato explícito de **20/5/25 buzones por hora** y **tope de 750 acumulados por cuenta** ([[2026-1024-gptgrok2api-icloud-privacy-mail-fabrica-de-correo-con-techo-decreciente]])— es la variante **internalizada** de una partida que el mercado resuelve de cuatro maneras distintas: la **función de biblioteca** (el bot genera el buzón con `generator.email`, recoge el OTP solo, coste marginal cero —una inferencia de diseño, no un precio medido—), el **proveedor pago y automatizable** (NotLetters, 0.05 ₽, web + HTTP API + IMAP sin documentar), el **proveedor gratuito y manual** (EmailOnDeck, ni una cifra, sin superficie programable) y la **suscripción de equipo para QA** (MailS.ac, desde $18/mes) ([[2026-1024-chatgpt-creator-correo-temporal-y-otp-automatico-con-generator-email]], [[2026-1026-mailsac-plan-gratuito-con-una-direccion-privada-y-pagos-desde-18-dolares-al-mes]]).

La lectura para la decisión build-vs-buy es una **columna que hoy no existe en la comparación**: no solo "coste por buzón", sino **"¿la unidad es automatizable?"** y **"¿el buzón es privado?"**. MailS.ac publica la respuesta a la segunda en su home: "**anyone can read an @mailsac.com inbox**, so use made-up data" — y por eso su propio producto es **exactamente el contrario** del de este repo: existe para **probar el formulario de alta de uno mismo** ("Mailsac is built for testing email… check sign-up confirmations, password resets and one-time codes"), no para dar de alta a terceros ([[2026-1026-mailsac-correo-desechable-para-testing-de-qa-y-no-de-registro-masivo]], [[2026-1026-mailsac-los-buzones-publicos-son-legibles-por-cualquiera]]).

Y hay un elemento de arquitectura que el mercado **ya externaliza** y que este repo tiene pendiente: el **dominio de prueba como producto**. MailS.ac vende el "**Zero Setup Subdomain service**" —"Create subdomains in seconds"— y el **BYOD** ("You can also bring your own domain!"), es decir, la configuración DNS/MX del cliente resuelta por un tercero, con el subdominio como unidad de organization ("Categorize workflows, email testing phases or different testing teams") ([[2026-1026-mailsac-subdominios-en-segundos-y-idioma-de-dominio-propio]]). Y también el **Email Capture service**, que asume el fallo de routing ("ensuring email doesn't get sent to live users") ([[2026-1026-mailsac-email-capture-para-evitar-correos-a-clientes-reales]]). El límite de ambas externalizaciones es el mismo: **ninguna puede resolver la marca del remitente**, y un producto multi-tenant necesita que el cliente vea **su propio** dominio en el `From`.

**El correo tiene cinco regímenes, y solo uno sirve a un pipeline sin construir nada.** La línea de aprovisionamiento que este repo internaliza —cinco proveedores de correo más el sidecar de iCloud Privacy Mail, con contrato explícito de **20/5/25 buzones por hora** y **tope de 750 acumulados por cuenta** ([[2026-1024-gptgrok2api-icloud-privacy-mail-fabrica-de-correo-con-techo-decreciente]])— es la variante **internalizada** de una partida que el mercado resuelve de cinco maneras: la **función de biblioteca** (el bot genera el buzón con `generator.email`, coste marginal cero), el **proveedor pago y automatizable** (NotLetters, 0.05 ₽, web + API + IMAP), el **proveedor gratuito y manual** (EmailOnDeck, sin precio ni API), la **suscripción de equipo para QA** (MailS.ac, desde $18/mes) y —nuevo— el **proveedor gratuito, automatizable y documentado**: mail.tm, que da buzón y clave **al abrir la página**, declara "API access" y "a quick way to register disposable mailboxes in bulk", y **enlaza su documentación** en `docs.mail.tm/` ([[2026-1026-mail-tm-buzon-y-contrasena-nacen-al-abrir-el-sitio]], [[2026-1026-mail-tm-alta-masiva-de-buzones-y-api-declaradas-en-la-home]]).

La lectura para la decisión build-vs-buy es que **el repo ya internalizó el tramo que el mercado ya no obliga a construir**, pero que internalizar **no es la misma cosa que externalizar gratis**: mail.tm muestra que el generador propio de buzones se puede sustituir por un proveedor —y el propio vault lo tiene registrado como "Funciona, pero NotLetters es mejor para producción" ([[2026-1026-mail-tm-el-farm-del-vault-ya-lo-usa-con-dominio-propio-y-clave-determinista]])—, mientras que la razón de internalizar **sigue siendo el dominio, no el buzón**: el valor está en el dominio propio, que es el activo que se bloquea y que el bot persiste en un `blacklist.json` cuando falla ([[2026-1024-chatgpt-creator-blacklist-de-dominios-persistida-en-archivo]]). Por eso la comparación relevante **no es buzón contra buzón, sino dominio contra dominio**, y mail.tm —que publica **dos marcas de dominio** (`mail.tm` y `Mail.gw`) y **cero geografía** ([[2026-1026-mail-tm-mail-gw-como-marca-hermana-en-la-navegacion]])— es la señal de que **en este sector la superficie de marca es la cobertura real**.

Y hay una lección de seguridad que esta captura deja escrita para el repo: mail.tm promete "**kept forever**", "unlimited number" y "no limit", con una clave "**unique, automatically generated**" y "Nobody but you can see what's inside" ([[2026-1026-mail-tm-buzon-conservado-para-siempre-y-sin-limite-de-unidades]]). Eso convierte el buzón en **activo acumulativo y persistente**, no en consumible —el perfil de credencial, no de insumo— y, si la clave no es realmente aleatoria, en **pasivo que hay que rotar**. El repo, que sí conoce el contrato de techo y temporizador del sidecar, tiene aquí su referencia de qué pasa cuando el contrato **lo pone el proveedor y no el repo**: no hay techo, no hay temporizador y no hay borrado.
- **Captcha**: **internalizado**, no comprado —`captcha-solver/` con navegador real (Chromium/CloakBrowser) en Docker/Xvfb, concurrencia dinámica, proxy por petición y reciclaje del navegador ([[2026-1024-gptgrok2api-registro-protocolo-sin-navegador-y-captcha-solver-integrado]]). El coste pasa de **$ por 1000** a **coste de infraestructura** que escala con altas simultáneas.
- **IP**: **jerarquía de salidas** —proxy global, proxy por cuenta, grupos, límite de concurrencia por nodo, salida de reserva, WARP + Privoxy (SOCKS5→HTTP) y FlareSolverr, con **salida sticky compartida en las tres fases del checkout** y rotación continua solo en la promoción ([[2026-1024-gptgrok2api-stack-warp-privoxy-flaresolverr-como-salida-estable]]).

Y añade una pieza que el thread no tenía: **la gestión del ciclo de vida de la credencial**. El sondeo corre cada 60 minutos en lotes de 50 y distingue **tres estados** —inválido (se relee correo y contraseña y se reintenta), desconocido por timeout (no se toca nada) y no efectivo por cuota (un `402` **no** es un fallo de autenticación)— con backoff **1/2/4/8/16/24 h** para lo recuperable y **60/120/300 s** para lo bloqueado por cuota ([[2026-1024-gptgrok2api-sondeo-y-recuperacion-automatica-de-cuentas-grok]]). La taxonomía de tres estados es la pieza transferible: **cada clasificación errónea destruye capacidad**.

El dato de negocio que cierra la sección es el de la **cadena de valor vista desde el productor**: tras un registro de Grok exitoso la cuenta entra en una cola de prioridad de OAuth con 2 workers y **se entrega a NovaApi y a CPA** según configuración; la integración con Sub2API usa `Base URL: http://gptgrok2api/v1` y el alias de red Docker `gptgrok2api`. El README advierte que un Sub2API normal puede carecer del tipo de cuenta OAuth de xAI y que la imagen por defecto `weishaw/sub2api:latest` puede no servir ([[2026-1024-gptgrok2api-sub2api-novaapi-como-destino-de-las-cuentas-registradas]]). Es decir: **el mismo repo documenta el eslabón anterior al relay** —proveedor de correo → gateway de registro → relay → mercado de reventa— y con ello **presiona la atribución "Sub2API vs New API" de PriceAI**, que describe la capa comercial del escaparate y no el aprovisionamiento ([[2026-1023-priceai-transit-canal-tipo-sub2api-vs-new-api]]).

Sobre el captcha hay una fricción viva que esta sección deja planteada y que corresponde al thread de economía de la verificación y reventa de cuentas: el captcha se ha medido allí como **commodity de catálogo** (2Captcha: $0,5–$2,99 por 1000, 1–2 s; solo FunCaptcha a $50 y ALTCHA a $2,99 son caros y lentos; [[2026-1024-2captcha-precios-por-1000-por-tipo-de-captcha]]), mientras que aquí se **internaliza**. La consecuencia aritmética es que **el criterio de coste de esta partida depende de la tasa de altas simultáneas, no del volumen total**, y por eso no puede comprarse con un catálogo de precios por 1000; es también la respuesta a la fricción 13 de ese thread (hCaptcha y Geetest no cotizables con el catálogo publicado): **una solver propia no tiene la restricción de catálogo**. El punto queda registrado aquí y **tiene fricción numerada en el thread de economía** —la 38 de [[economia-de-la-verificacion-y-reventa-de-cuentas]]—: la aritmética de la partida cambia según la tasa de altas simultáneas.

### Una cuarta edición del arquetipo: el puente que no fabrica la cuenta, administra las cookies

La sección de este thread que describe el arquetipo del puente no oficial —Discord → API en `midjourney-proxy`, gateway que además fabrica la cuenta en `gptGrok2api`— tiene ahora **una cuarta edición medida**, y es la que más directamente se parece al producto propio porque su valor está en la **capa de gestión de credenciales**, no en la llamada.

`wlhtea/Suno2openai` (275 estrellas, 49 forks, Python, MIT, 3.202 KB) se describe en su `description` bilingüe como una llamada a la API de Suno **en formato OpenAI** que además **guarda las cookies en una base de datos para realizar las llamadas desde un pool de cookies** ([[2026-1026-github-search-suno-pool-de-cookies-y-relay-newapi-oneapi]]). Es decir: **la capa de *pool de cuentas* y la capa de *API compatible* en el mismo artefacto**, exactamente el salto que este thread describe entre producir capacidad y venderla. Y el dato de integración es el que lo ata al mercado que el producto propio también mira: el repo declara estar **integrado en las estaciones de reventa `newapi` y `oneapi`**, con adapters para front-ends como `chat-next-web` — es decir, **un upstream más de los gateways de agregación**, no un servicio aislado.

**La comparación con `gptGrok2api` es lo que hace útil la medida.** Allí el pool se alimentaba de un registrador integrado con captcha solver propio ([[2026-1024-gptgrok2api-registro-protocolo-sin-navegador-y-captcha-solver-integrado]]); aquí el pool se alimenta de **cookies ya existentes, guardadas en base de datos y rotadas**, y el aprovisionamiento es radicalmente distinto: no hay registro, hay **recolección de sesión**. Es la misma arquitectura de negocio —vender capacidad de una plataforma sin API oficial— con un coste de aprovisionamiento que no pasa por el correo, ni por el captcha, ni por el SMS, sino por **la acumulación de sesiones válidas**. Para un producto que hoy sirve inferencia con un puntero a un proveedor, esto es la lectura incómoda: **el activo defendible de esta categoría no es el código del puente, es el pool de credenciales**, y el pool no se compra en un catálogo, se acumula.

Hay además un dato de ventana de coste que la categoría aporta y que el thread no tenía: `ShowSnowBlood/suno-api-plus` (1 estrella, 1 fork, TypeScript, **LGPL-3.0**, 50.893 KB, topics `docker`, `music-generation`, `nextjs`, `openai-api`, `self-hosted`, `suno`) describe *"Enhanced Suno API with admin dashboard, multi-account pool, OpenAI-compatible auth, YesCaptcha/2Captcha, cookie tools"* ([[2026-1026-github-search-suno-api-plus-pool-de-cuentas-y-captcha-comprado]]). Es el **único item del corpus que nombra proveedores de captcha** y el único que declara panel de administración y pool multicuenta con autenticación compatible con OpenAI. Con la tabla de precios del vault —2Captcha entre $0,5 y $2,99 por 1000 en los tipos estándar ([[2026-1024-2captcha-precios-por-1000-por-tipo-de-captcha]])— esta partida **sí es cotizable**: es $/1000, no infraestructura. Y la **única licencia copyleft en los dos corpus de repositorios indexados por la API de búsqueda** (LGPL-3.0) corresponde precisamente al artefacto que expone una superficie de administración y un pool de credenciales: software que se licencia con atribución y permiso de modificación, no el script MIT.

**Y hay una cuarta señal, la de la distribución, que el thread de arquitectura debería leer con atención.** `wesleysimplicio/PiAPI-Skills` (6 estrellas, 0 forks, TypeScript, MIT, 41.791 KB, **20 topics**) se describe como un *"skill bundle for Claude, Codex, **Hermes**, OpenClaw, Cursor, Windsurf, and generic agents"* que cubre PiAPI y sus servicios —Midjourney, Suno, Kling, Flux, Hailuo, Luma, Hunyuan, Faceswap, Trellis 3D, MMAudio, F5-TTS, Veo 3, Gemini 2.5 Flash Image, Seedance y *"the OpenAI-compatible LLM gateway"* ([[2026-1026-github-search-suno-piapi-skills-un-bundle-de-skills-para-agentes-con-hermes]]). El detalle relevante para este vault es que **la propia plataforma aparece nombrada por un actor externo como cliente objetivo**, junto a Claude Code, Codex, Cursor, OpenClaw y Windsurf. Es decir: **el producto que un proveedor de relays quiere instalar no es un SDK ni una documentación, es un bundle de skills para agentes**, y Suno deja de ser un endpoint para ser **una de las 16 habilidades declaradas** de un bundle portable entre siete harnesses. Para un producto que sirve inferencia a tenants, la distribución se está moviendo del API-key al skill, y ese es un mercado que MyOwnClone no está midiendo.

**Lo que cambia en la lectura de build-vs-buy.** La sección de este thread concluía que "lo que no hay que hacer es comprar inferencia en el 中转 sin asumir que es una caja negra" y que "la capa que no se compra: el control de acceso". Esta captura añade que **el otro lado de esa caja negra es un pool de cookies con rotación, panel de administración y captcha de catálogo** —es decir, **capacidad que se fabrica por acumulación de sesiones y se ofrece con formato OpenAI** ([[2026-1026-github-search-suno-noventa-y-ocho-por-ciento-de-las-estrellas-en-cuatro-repos]]). La consecuencia de arquitectura es que un gateway propio no se limita a sustituir un puntero: **el pool de credenciales es la parte que el producto tendría que fabricar si quisiera no depender del relay**, y esa es una línea de trabajo con coste recurrente y no con precio de lista.

**Y un dato de higiene que hay que registrar, porque afecta a cómo se lee el mercado.** Dos de los cuatro repositorios con más estrellas de la consulta **no son herramientas de Suno**: `whataicc/doc-whataicc-api` (37 estrellas) y `Token173/doc-token173-api` (27 estrellas) son **documentación en chino de estaciones de reventa** —"支持Claude、Midjourney、Suno、OpenAI等650+模型教程" y "支持Claude、GPT、Gemini、Grok、Midjourney、Suno、OpenAI等500+模型教程，SLA99.9%"— con `homepage` `https://api.whatai.cc` y `https://www.token173.net` ([[2026-1026-github-search-suno-dos-de-los-cuatro-primeros-son-tutoriales-de-relays-chinos]]). Es decir: **el marketing de los relays ocupa dos de las cuatro primeras posiciones de la categoría**, y dos estaciones que **no aparecen en los inventarios del vault** (PriceAI, VeriDrop) publican **número de modelos y SLA declarado** sin que nada verificable las respalde. Para un producto que compite en la capa de agregación, la conclusión es incómoda y concreta: **el corpus público de esta categoría está contaminado por sus propios intermediarios**, y cualquiera que mida el sector con una búsqueda por nombre de herramienta va a medir, en parte, la capacidad de SEO de los relays ([[2026-1026-github-search-suno-dieciocho-resultados-pero-solo-nueve-items-en-el-fichero]]).

### Una quinta edición del arquetipo: el gateway que expone una etiqueta de modelo falsa y no publica ni coste ni capacidad

La sección de este thread que describe el arquetipo del puente no oficial tiene ahora **una quinta edición medida**, y es la que más se parece al producto propio porque su valor está entero en la **capa de gestión de credenciales**, no en la llamada.

`wlhtea/Suno2openai` (275 estrellas, 49 forks, Python, MIT, 464 commits, último commit el 19 de enero de 2025) **no es una implementación musical original**: es una **capa wrapper/orquestadora** construida sobre `SunoSongsCreator` (yihong0618) y `Suno-API` (SunoAI-API), que expone el resultado en **interfaz compatible con OpenAI** ([[2026-1026-suno2openai-integrado-sobre-sunosongscreator-y-suno-api]]). Es decir: **la categoría no reimplementa el backend, lo envuelve y lo vende con el formato de otro**. La observación que el thread ya tenía sobre el arquetipo —"el puente es un envoltorio, el valor está en las credenciales"— queda aquí con su forma exacta: el envoltorio **gestiona cookies en base de datos y las rota** ([[2026-1026-suno2openai-el-pool-de-cookies-exige-mysql-como-requisito]]).

**El detalle de contrato que más importa a un producto que sirve inferencia a tenants es este: el campo `model` vale `gpt-3.5-turbo`.** El único ejemplo documentado del endpoint `POST /v1/chat/completions` usa `model: gpt-3.5-turbo`, `messages` y `stream` opcional, y **no hay catálogo de modelos de Suno ni mapeo entre modelos y capacidades** ([[2026-1026-suno2openai-el-campo-model-es-gpt-3-5-turbo-sobre-un-backend-de-musica]]). Es decir: **el backend es musical y el contrato dice OpenAI**, lo que significa que **un relay que reenvía este gateway no puede ofrecer una columna de "modelo" honesta**: cualquier cliente que pregunte qué modelo está usando recibe una etiqueta de compatibilidad, y el orden de prioridad entre relays y modelos se vuelve **indistinguible desde la petición**. Para un producto de agregación, esto es el problema operativo central: **la ausencia de un modelo real no es una inconvenience estética, es la razón por la que un gateway no puede enrutar por calidad ni cotizar por modelo**.

**La segunda lectura de arquitectura es la de la madurez del artefacto, y es desfavorable.** El proyecto **no publica releases, ni changelog, ni SLA, ni hoja de ruta fechada**; el soporte es un **correo QQ** y la página ofrece **prácticas a estudiantes** — es un proyecto unipersonal, con la estructura de operación de un trabajo de fin de carrera, no de una infraestructura ([[2026-1026-suno2openai-proyecto-unipersonal-con-practicas-y-email-qq]]). Y la distribución es **una imagen `wlhtea/suno2openai:latest` sin versión fijable**, con la guía de `docker-compose` fechada el **7 de abril de 2024**, dos meses antes del último commit ([[2026-1026-suno2openai-imagen-docker-sin-versionar-y-documentacion-fija]]).

**Y hay una pieza de capacidad que el thread debe leer como advertencia de diseño.** La rotación de cookies está **implementada** —cuatro endpoints REST de administración del pool— pero la **cola de peticiones figura en "Future Plans"**: se rotan las credenciales y no se serializan las peticiones ([[2026-1026-suno2openai-rotacion-de-cookies-declarada-sin-cola-de-peticiones]]). Es el **contorno exacto del límite**: un pool sin cola no es una capacidad, es un **conjunto de cookies con presupuesto de API**. La lección de arquitectura que el thread debería extraer es que **la concurrencia no viene del pool de credenciales sino de la cola**, y que un proyecto que confunde ambas cosas está vendiendo un límite que no ha medido.

La negativa: **la inferencia hoy es una dependencia, no una arquitectura** —un `OPENAI_API_BASE` a DeepSeek, sin router, sin precios por uso y sin failover ([[2026-1022-gap-dify-como-capa-inferencia-prompts]]). La positiva: **el mercado de esa capa tiene su propia arquitectura medible**, el gateway New API, con grupos como eje de precio y multiplicadores de 0,04x a 7,00x ([[2026-1023-new-api-grupos-como-eje-de-precio-del-relay]], [[2026-1023-priceai-transit-dispersion-de-multiplicadores]]).

El thread ya registró el problema equivalente en el otro extremo —la tabla oficial que mezcla **requests, prompts, credits y dólares de uso** sin columna de conversión ([[2026-1023-priceai-codificacion-por-requests-vs-prompts-vs-creditos]])— y ahora tiene **el mismo problema con la unidad resuelta en un extremo**: Heroku publica las unidades una por tabla y sin convertirlas. La diferencia es que **aquí el vault puede compararlas con las suyas**: el embeddings del producto es `text-embedding-3` de OpenAI ([[2026-1022-pgvector-embeddings-openai-inferidos]]) y el de Voyage en el competidor ([[2026-1022-myclone-viaje-embeddings-voyage]]); el rerank es la pieza que New API expone como endpoint (`/v1/rerank`) y que hoy no existe en el producto ([[2026-1023-new-api-gateway-unificado-de-modelos]]).

**Y una quinta corrección, que es la que más pesa para el negocio: hay un precio de lista para el consumo de inferencia de un competidor con el mismo modelo base.** El producto factura por tenant con un desglose **por proveedor (Anthropic + OpenAI)** ([[2026-1022-costes-por-categoria-tenant]]). Con esta tabla, el vault puede por primera vez **auditar si un relay es más barato que comprar el token**: si la columna de proveedor del panel dice Anthropic y el multiplicador efectivo del canal es 1,0x–2,0x, **el margen del relay es directamente el sobrecoste frente a una lista de $5.50/$27.50 por 1M en Opus 4.8**; y si es 0,05x, **el relay vende el mismo token por debajo de la lista y solo es explicable por capacidad o por riesgo de cumplimiento**. Ese es el dato que decide si construir gateway propio es una decisión de arquitectura o una decisión de margen.

**Lo que queda abierto, y es lo que el hilo debe dejar escrito.** La tabla **no publica SLA, no publica throughput, no publica límites de tasa y no publica qué región se factura cuando el modelo es "US | EU"**; y el bloque de soporte publica **Basic gratis** y remite Standard, Premier y Signature a "contact sales" sin importes ([[2026-1026-heroku-soporte-basico-gratis-y-success-plans-enterprise]]). Los MCP sí tienen un modelo declarado —**dynos one-off con pay-as-you-go**— pero **sin tabla de precios** ([[2026-1026-heroku-mcp-servers-con-dynos-one-off-pay-as-you-go]]), y los add-ons de Elements solo se cotizan en el Marketplace, con **1 crédito = $1** para clientes Enterprise ([[2026-1026-heroku-elements-1-credito-igual-a-1-dolar-solo-enterprise]]). Es decir: **la parte de cómputo de datos y la de inferencia están cotizadas al centavo; la de soporte, integración y agentes no lo está**. Para un producto que necesita facturación al tenant, esa es la frontera exacta entre lo que puede presupuestarse y lo que no.

### Qué significa para el build-vs-buy

Lo que la evidencia deja es una posición, no un plan:

1. **El `OPENAI_API_BASE` es un límite de arquitectura disfrazado de variable de entorno.** Un gateway convierte "proveedor" en "canal + grupo + precio"; aquí el proveedor es una constante. Mezclar proveedores, o caer a un relay cuando el upstream falla, requiere hoy tocar configuración y redeploy. Un gateway es **la abstracción que falta** — no un lujo de escala.
2. **Lo que un gateway compra, en orden de valor para este producto:** (a) un solo endpoint y una sola credencial para proveedor y embeddings; (b) coste medido por token con contabilidad honesta, en lugar de la atribución por proveedor que hoy infiere el panel; (c) failover entre canales, imposible con un puntero único; (d) la capacidad de vender a un tenant el mismo modelo con márgenes distintos sin duplicar el stack.
3. **Lo que cuesta, con nombres:** AGPLv3 con atribución visible en la interfaz ([[2026-1023-new-api-licencia-agplv3-y-atribucion-en-ui]]), que choca con la marca propia y con la ausencia de repos públicos; **app + Postgres + Redis** sobre una infraestructura hoy stateless en nginx ([[2026-1023-new-api-despliegue-postgres-redis-y-clickhouse]]); y el coste real de la conversión multi-protocolo, que el propio proyecto declara con pérdida de campos ([[2026-1023-new-api-relaykit-conversion-perdida-de-campos]]). El suelo de self-hosting del sector lo ponen los patrocinadores chinos de VPS (Aliyun 2核2G "desde 68 元/año", Tencent 2核4G "desde 199 元/año", ambos con copy que menciona montar un relay propio) — son declaraciones de sponsor, sin SLA ni verificación, no un precio confirmado ([[2026-1023-priceai-sponsors-vps-chinos-para-auto-hospedar-relay]]).
4. **Lo que no hay que hacer:** comprar inferencia en el 中转 sin asumir que es una caja negra. Sin SLA ([[2026-1023-priceai-descargo-de-responsabilidad-sin-sla]]), con verificación de modelo pendiente, con 号池 compartido y con dispersión de multiplicador de casi dos órdenes de magnitud —es decir, con un multiplicador que puede ser margen, error de conteo o ambas cosas ([[2026-1023-new-api-tokenkit-conteo-de-tokens-calibrado]]). Para un producto que factura al tenant por uso, un canal sin SLA es un coste que se paga en incertidumbre.
5. **Y la capa que no se compra:** el control de acceso. El vault hoy sirve `/api/clones`, `/api/inbox` y `/api/clones/x/prompts` con `401` pero expone `/api/auth/session` en 200, sin rate limiting ([[2026-1022-sin-rate-limiting]]), en un nginx sin cookies seguras ([[2026-1022-cookie-next-locale-sin-httponly-ni-secure]]) y con toda la IA y la autenticación en servidor ([[2026-1022-ia-y-auth-totalmente-servidor]]). El gateway resuelve el lado del consumo, no el del borde.

## El hallazgo estructural: dos productos, no uno

[[2026-1022-myownclone-dos-repos-flask-nextjs]] — MyOwnClone no es un monorepo. Son **dos bases de código con procesos de arranque separados**:

| Capa | Ubicación | Arranque | Acceso a datos |
|---|---|---|---|
| Backend Flask/SQLAlchemy | `api/` (`controllers/myownclone_public.py`, `controllers/console/myownclone/*`, `models/{clone,analytics}.py`, `core/retrieval.py`, `core/myownclone/{email_ai,silos}.py`) | `python -m api.app_factory`, puerto 5001 | SQLAlchemy |
| Frontend Next.js/Drizzle | `src/app/(dashboard)/*`, `src/lib/db/schema/*` | `npm run dev`, puerto 3000 | **Drizzle directo** |

El frontend tiene su propia ruta `src/app/api/clone/memories/route.ts` que **no pasa por Flask**. De ahí sale el segundo hallazgo: [[2026-1022-auth-flask-nextauth-desconectados]] — dos sistemas de identidad conviviendo sobre el mismo modelo de datos. Flask usa `@login_required`, `@account_initialization_required`, `@setup_required`; el frontend usa `auth()` de NextAuth. Ninguno gobierna al otro. La fricción con [[2026-1022-myownclone-jwt-token-required]] (que exige `@token_required` como patrón) sugiere que existen tres decoradores y dos o tres mecanismos coexistiendo en la misma base de datos.

## La superficie real del producto

[[2026-1022-mapa-modulos-internos-desde-bundles-js]] reconstruye el mapa completo desde 15 bundles (~1,2 MB) en dos capas:

## El pipeline de chat, paso a paso

[[2026-1022-pipeline-chat-actual-myownclone]] — el camino real de `POST /api/myownclone/public/clones/{slug}/chat`:

1. `CloneConfig` por slug
2. `CloneModePrompt` por `clone_id` + modo activo
3. `_add_memories_to_prompt()` — concatena memorias al system prompt
4. `retrieve_from_silo()` — RAG sobre el dataset de Dify
5. `full_prompt = system_prompt + CONTEXT + user_message`
6. `model_instance.invoke_llm_stream()` → SSE `data: {content: chunk}` hasta `data: [DONE]`

Dos consecuencias: el prompt se almacena **sin historial** (cada `PUT` sobrescribe), y la recuperación es contra **Dify como capa de inferencia** ([[2026-1022-gap-dify-como-capa-inferencia-prompts]]) — lo que implica que todo cambio de prompt pasa por Dify y que la compilación de variables (`{name}`, `{role}`) tiene que ocurrir antes de enviar al modelo, con sintaxis `{{variable}}` como MyClone.is.

## Por qué no hay API (y por qué no es solo una decisión)

[[2026-1022-ia-y-auth-totalmente-servidor]] — ningún bundle contiene claves ni endpoints de OpenAI, Anthropic, Cohere, Supabase, Auth0, Clerk o NextAuth. Las únicas salidas a terceros son PostHog (`eu.i.posthog.com/i/v1/logs`) y Sentry (`sentry.io`). No hay tRPC, WebSocket ni SSE de negocio en el cliente.

No es que exista una API privada: es que **no hay API**. La fricción con [[2026-1022-myclone-api-rest]] (que decía que MyOwnClone expone OpenAPI) queda sin resolver — el checkout local de Dify en el vault no es la API pública del producto.

[[2026-1022-pgvector-embeddings-openai-inferidos]] infiere PGvector + `text-embedding-3` de OpenAI por extensión de Neon, y marca los LLM como Anthropic Claude + OpenAI por strings de tracking de coste — en tensión directa con la opacidad total de arriba.

### La capa de soporte como parte de la arquitectura: qué pasa cuando el PaaS te rompe el canal cifrado

La captura de `https://support.heroku.com/` (2026-10-25) aporta a este thread una evidencia que no es de código sino de **contrato operativo**, y que toca una decisión de arquitectura ya tomada: **autoalojar los datos gestionados**.

El caso es concreto y está en la propia home de soporte de Heroku: **"Heroku Key-Value Store Upgrade - SSL/TLS Connection Issues" está entre los cinco contenidos más leídos del portal** ([[2026-1026-heroku-key-value-store-upgrade-con-problemas-de-ssl-tls]]). Es decir, **el ciclo de upgrade de un servicio de datos gestionado puede romper el canal cifrado de las apps existentes**. Y el catálogo del Key-Value Store, con sus 25 planes desde Mini $3 hasta Shield-14, declara en todos ellos "High availability with low-latency failover" ([[2026-1026-heroku-key-value-store-mini-3-dolares-hasta-12500]]). **La alta disponibilidad y el failover son estados; la transición de versión es un evento, y los eventos no están cubiertos por el estado.** Eso no lo dice el proveedor: lo dice la foto de su propia pantalla de soporte.

La lección de arquitectura, aplicada a este producto: **el riesgo no está en el runtime del dato, está en el canal y en quién puede cambiarlo**. Una app que habla con Redis por TLS tiene, en un PaaS gestionado, **dos variables de versión en producción**: la suya y la del proveedor, y la segunda la mueve un tercero en un día que el cliente no controla. Con nginx + Postgres + Redis autoalojados ([[2026-1022-live-verify-deployment-migrada-a-vps-nginx]]) esa segunda variable no existe, y el vault no tiene que presupuestar el riesgo de un corte de servicio por cambio de versión del Redis de otro.

La segunda observación es de ciclo de vida, y va en la misma dirección: **Heroku declara EOL de runtime como contenido de soporte de primer nivel** —el "Heroku-22 End-of-Life FAQ" está entre los cinco artículos más leídos ([[2026-1026-heroku-22-end-of-life-faq-como-articulo-de-tendencia]])— y el changelog del portal publica el runtime por defecto de las apps nuevas como métrica separada (Ruby 3.4.12, seis SDK de .NET, seis JDK de 1.8.0_512 a 27.0.1) ([[2026-1026-heroku-changelog-de-runtimes-ruby-3-4-12-opjdk-y-dotnet]]). Es la misma forma de obsolescencia que ya se midió en las generaciones de cómputo: las familias Private/Shield de Cedar no valen para los espacios Fir ([[2026-1026-heroku-fir-dynos-kubernetes-todos-requieren-private-space-desde-25]]). **La diferencia con el stack propio es que aquí no hay nadie que pueda declarar EOL sobre la infraestructura**: no hay versión del runtime que una plataforma pueda retirar, ni una ventana de migración que el proveedor defina. Para un producto que vende clones de personas y cuyo activo es el corpus y el modelo, esa estabilidad del substrate es una decisión de arquitectura, no un detalle de despliegue.

Y el tercer elemento, que es de proceso y no de stack: **el soporte de un PaaS enterprise no es un extra, es un producto con circuito comercial propio** —tres planes Standard/Premier/Signature sin precio ni SLA publicado ([[2026-1026-heroku-soporte-basico-gratis-y-success-plans-enterprise]]), un directorio propio `help.heroku.com/enterprise` para clientes Enterprise ([[2026-1026-heroku-enterprise-resources-como-seccion-propia-del-soporte]]) y una puerta disuasoria en el propio artículo más leído del portal: "Before opening a support ticket" ([[2026-1026-heroku-soporte-articulo-mas-tendido-es-instruccion-para-no-abrir-ticket]]). La versión interna del producto es la contraria: **soporte gratis, asistido por IA, con SLA declarado** ([[2026-1022-soporte-al-cliente-separado-y-escalado]]). Es la diferencia entre un producto que compra su servicio de soporte y uno que lo es.

## La capa vectorial: lo que el código hace y lo que el compose promete

La §"El stack, verificado" de este thread sitúa la capa de datos en Neon (PostgreSQL serverless) e infiere PGvector con `text-embedding-3` ([[2026-1022-neon-postgres-serverless]], [[2026-1022-pgvector-embeddings-openai-inferidos]]). La lectura directa del repositorio del producto —`ops/docker-compose.backend.prod.yml`, `api/docker-compose.yml`, `api/core/retrieval.py`, `api/core/rag/datasource/retrieval_service.py`, `api/models/knowledge.py`, `api/requirements.txt`— permite cerrar esa pregunta: **el producto despliega Weaviate como proceso separado, no lo usa, y su búsqueda vectorial real es un escaneo en Python sobre Postgres**. Es el hallazgo más accionable de la tanda, y va aquí y en [[escala-de-hosting-barato-y-el-limite-de-4-euros]], porque cambia la aritmética de RAM del stack contra el techo de ≤ €4/mes.

### Lo que el compose promete

El `docker-compose` de producción (`ops/docker-compose.backend.prod.yml`) declara cuatro servicios con límites de memoria explícitos:

| Servicio | Límite de memoria | Reserva | CPU |
|---|---|---|---|
| Postgres (`db_postgres`) | 2 GiB | 512 MiB | — |
| Redis | 256 MiB | 64 MiB | — |
| **Weaviate 1.24.0** | **1 GiB** | **256 MiB** | — |
| API (Flask) | 1 GiB | 256 MiB | 1.0 |

Son **4,25 GiB de límites y 1,06 GiB de reservas** en un stack que el thread describe como "nginx + Postgres + Redis + Flask/Next.js" sobre un VPS ([[2026-1022-live-verify-deployment-migrada-a-vps-nginx]]). El contenedor de Weaviate se publica solo en `127.0.0.1:8080`, con autenticación por API key habilitada y acceso anónimo deshabilitado, `ENABLE_MODULES: text2vec-openai,text2vec-huggingface` y volumen persistente `weaviate_data`. El servicio `api` **recibe `WEAVIATE_URL` y `WEAVIATE_API_KEY` por `environment`** —es decir, el contrato de integración está cableado— y `api/.env` define ambas variables.

### Lo que el código usa: nada

Tres medidas, todas por lectura estática del código:

1. `grep -rn "weaviate" --include=*.py api/` devuelve **cero coincidencias** fuera de `.venv/`. En el repositorio entero, las únicas menciones en Python son `conftest.py` (fija `WEAVIATE_API_KEY` a un valor de test) y un comentario en `tests/test_smoke.py`. **No hay ninguna llamada `weaviate_client.connect()` ni ninguna consulta a `http://weaviate:8080`.**
2. `api/requirements.txt:8` declara `weaviate-client>=4.4.0`, pero **ningún módulo lo importa**. La dependencia está instalada y sin usar.
3. `grep` de `WEAVIATE_URL` y `WEAVIATE_API_KEY` sobre el código Python de la API devuelve **cero lecturas**: el compose pasa las variables y la aplicación no las consulta.

### Lo que el retrieval hace de verdad

La ruta de retrieval efectiva es `api/core/retrieval.py`. La función `retrieve_from_silo()` entra primero en `_retrieve_from_local_chunks()`, que hace un `select(Chunk, Source)` contra Postgres filtrando por `Source.clone_id` y `Source.status == "ready"`, y puntúa los chunks **en Python puro**:

- `_terms()` extrae términos de ≥3 caracteres y filtra una lista de stopwords; `_lexical_score()` es **solapamiento léxico** (Jaccard) contra el contenido del chunk.
- `_lexical_embedding()` construye un vector de **1.536 dimensiones** proyectando cada término con un hash FNV-1a (`_hash_term`, constante 2166136261, primo 16777619) sobre el índice `hashed % 1536`, con signo según la paridad. **No es un embedding de modelo**: es una proyección hash del término, normalizada.
- `_cosine_similarity()` compara ese vector con `chunk.embedding` y el score final es `max(term_score, vector_score)` — una mezcla híbrida léxica/vectorial calculada en el proceso Python.

Dos detalles que cierran el círculo: `chunks.embedding` está declarado en `api/models/knowledge.py:30` como `mapped_column(sa.ARRAY(Float))`, es decir **un array de PostgreSQL, no una columna de tipo `vector` de pgvector**; y la rama que debería delegar en el motor externo (`api/core/rag/datasource/retrieval_service.py`) es un **stub de 16 líneas** cuyo `retrieve()` devuelve `{"segments": [], "total": 0}` y cuyo `__getattr__` devuelve `None` para cualquier atributo.

Es decir: **ni Weaviate ni PGvector hacen el trabajo de similitud**. La búsqueda es un escaneo completo de los chunks del clon en cada consulta, con un pseudo-embedding de hash, dentro del proceso de la API. La arquitectura de recuperación que la documentación de Dify sugiere ([[2026-1022-gap-dify-como-capa-inferencia-prompts]]) no es lo que este código ejecuta en la ruta local.

### Nota de método (lectura de código, no ejecución)

Todo lo anterior es **lectura estática de código**, no verificación en ejecución: no se ha levantado el stack, ni consultado el contenedor de Weaviate en producción, ni medido un recall, ni comparado el resultado de `retrieve_from_silo()` con lo que devolvería una consulta real al vector store. Lo que sí queda establecido por el código es la **ausencia de uso**: sin una lectura de `WEAVIATE_URL` en ningún módulo, el contenedor no puede estar en el camino de la búsqueda. Lo que no queda establecido —y queda **marcado para juicio humano, no auto-resuelto**— es si el vector store es **código muerto por abandono** (una decisión pendiente de tomar) o si **hay un consumidor fuera del repositorio** (un job, un script de ingesta, un cliente externo o una ruta que aún no se ha escrito). Esa distinción decide si la acción es *borrar* o *conectar*.

Nota lateral de higiene: `api/.env` contiene una **clave de API de Weaviate estática en claro** en el árbol de trabajo. No está versionada (`.gitignore` excluye `.env` y `git ls-files` no la lista), pero está en disco junto al código y se reutiliza por el compose. Si el contenedor se mantiene, la clave rotaría; si se elimina, la clave desaparece con él.

## La capa de identidad: por qué el auth casero sigue siendo la decisión correcta, y qué la cambiaría

Este producto **no tiene un proveedor de identidad**: su capa de auth es Flask + NextAuth coexistiendo sobre el mismo modelo de datos, con tres decoradores y dos mecanismos ([[2026-1022-auth-flask-nextauth-desconectados]], [[2026-1022-myownclone-jwt-token-required]]), y ningún bundle contiene claves ni endpoints de Auth0, Clerk ni WorkOS ([[2026-1022-ia-y-auth-totalmente-servidor]]). Es decir: **la capa de identidad es código propio**, y esa es una decisión, no un descuido.

La captura de precios del 2026-10-31 al 2026-11-02 (Auth0, Clerk y WorkOS) permite ahora **cuantificar por qué el auth casero es la decisión correcta hoy**, y con qué condición dejaría de serlo. El detalle completo está en [[economia-de-la-verificacion-y-reventa-de-cuentas]] §13; aquí solo importa la consecuencia arquitectónica, que es de una sola pregunta: **¿en qué unidad factura cada proveedor, y cuál de esas unidades es la unidad del producto?**

La unidad del producto es **el tenant**, y de hecho hay un tenant por creador con slug propio ([[2026-1022-multi-tenant-slug-unpublished]]). Aplicando la pregunta:

- Un proveedor que factura **por MAU** factura por una unidad que este producto no controla —el tráfico de un tenant— mientras que el valor comercial está en el número de tenants. Es la desalineación que hace que la partida de identidad crezca con el uso y no con el negocio.
- Un proveedor que factura **por organización retenida** factura exactamente en la unidad del producto: la partida de identidad se vuelve **una línea creciente en el número de tenants**, que es el eje que el thread de economía ya usa para separar "asiento" de "infra" ([[2026-1022-costes-por-categoria-tenant]]).
- Un proveedor que factura **por conexión**, donde una conexión es una empresa cliente, tiene una propiedad arquitectónica que el vault no había registrado: **el coste de identidad no escala con el uso**, y por tanto es compatible con un producto cuyo coste variable real es la inferencia por tenant.

Hay además una restricción que no es de precio sino de **límite de plan**, y que es el argumento más fuerte a favor del auth propio: los planes de Auth0 limitan **el número de tenants que se pueden incluir** (1 en Free, 3 en Essentials, 12 en Professional, ilimitado solo en Enterprise, que es el tramo "Contact us"). Un producto cuyo cliente **es** el tenant choca de frente con ese límite: el crecimiento comercial y el crecimiento de tenants **tienen que ir juntos**, y el segundo solo se compra en el plan que no publica precio. Es la misma forma de fricción que ya dejó anotada la capa de inferencia (**"no hay API"**, [[2026-1022-ia-y-auth-totalmente-servidor]]) y que la capa vectorial acaba de repetir: **cada dependencia que se compra de fuera llega con una forma de escalado que no es la del producto**.

Y hay un umbral cuantitativo que es el que decide esta sección. El coste del auth propio es una línea plana dentro del techo de ≤ €4/mes del stack. El primer trigger de un proveedor gestionado —una conexión SSO para un cliente enterprise— **se salta ese techo por sí solo**: una conexión SSO de Auth0 cuesta $100/mes y la segunda de Clerk $75/mes, es decir, entre 20 y 30 veces el presupuesto de hosting completo. La consecuencia arquitectónica es precisa: **en el diseño actual, mover la identidad a un proveedor gestionado no es una mejora del producto, es un salto de orden de magnitud en el coste fijo** — y solo se justifica si aparece una exigencia que el auth propio no puede cumplir.

¿Cuál sería esa exigencia? La captura responde una: **SAML/SCIM para clientes corporativos**, que es la única función que el producto no puede fabricar por su cuenta con un código de seis dígitos. Y hay una fecha que hay que tener delante al evaluarla: el Directory Sync de Clerk pasa a facturarse por separado **el 1 de enero de 2027**, de modo que el coste de una decisión de identidad tomada en 2026 puede cambiar sin que cambie el uso. Esto no es una hipótesis de roadmap: es una línea de precio con calendario.

Una consecuencia adicional, y es de diseño más que de coste: **SSO no es un feature, es un contrato de protocolo**. SAML y SCIM son superficies de integración que un producto que ya vive con NextAuth y Flask en dos repos tiene que sostener en dos repos, con dos configuraciones y dos rutas de callback. Es la razón por la que la comparación honesta no es "Auth0 es caro" sino "**el SSO corporativo tiene un coste de integración que no depende del proveedor**": el primer cliente SAML obliga a decidir **dónde vive el servicio de identidad del tenant** —dentro del producto, o en un proveedor que ya lo resuelve —, y esa decisión es de arquitectura, no de suscripción.

10. **Un gateway que expone compatibilidad sin modelo no se puede enrutar ni cotizar** — el campo `model` vale `gpt-3.5-turbo` sobre un backend musical, sin catálogo de modelos ([[2026-1026-suno2openai-el-campo-model-es-gpt-3-5-turbo-sobre-un-backend-de-musica]]); y el `AUTH_KEY` que protege las rutas de generación tiene como valor por defecto el timestamp de arranque ([[2026-1026-suno2openai-auth-key-por-defecto-es-el-timestamp-actual]]). 12. **La fricción 3 de este thread se resuelve contra la lectura del código: la capa vectorial declarada no existe como PGvector.** [[2026-1022-pgvector-embeddings-openai-inferidos]] infería PGvector + `text-embedding-3` de OpenAI "por extensión de Neon"; el código real declara `chunks.embedding` como `sa.ARRAY(Float)` y calcula la similitud en Python. Marcado para juicio humano, no auto-resuelto: lo que hay que decidir no es qué motor es "el bueno", sino si la capa vectorial es una **decisión tomada** o un **esqueleto heredado de una fase que nunca se completó**.
13. **Weaviate Cloud no es una opción para este producto, por tres razones independientes, y una de ellas es de arquitectura de producto.** El plan Free limita a **1 colección hasta 3 tenants** —inservible para "un clon por tenant"—, el Flex **empieza en $45/mes (≈ €40,91, ~10× el techo de ≤ €4/mes)** y el Premium **desde $400/mes** ([[2026-1029-weaviate-cloud-free-tier-100000-objetos-1gb-memoria]], [[2026-1029-weaviate-cloud-flex-minimo-45-dolares-al-mes]], [[2026-1029-weaviate-cloud-premium-desde-400-dolares-contrato-prepago]]). Pero el dato que de verdad decide es que **Weaviate no factura por objetos ni por consultas, sino por dimensiones vectoriales almacenadas** ($0,00465/1M en Flex): 100.000 objetos × 1.536 dimensiones = **153,6 M de dimensiones ≈ $0,71/mes** ([[2026-1029-weaviate-cobra-por-dimensiones-vectoriales-no-por-objetos]]). Es decir, **el mínimo de $45 domina el coste, no el uso** —y por tanto la decisión no es "cuánto indexamos" sino "aquí no existe un pay-as-you-go real". Lo que hace aún más dura la comparación es que **el self-hosted usa la misma base de datos Weaviate** y solo pierde tres servicios (Embedding Service, Query Agent, Data Import) ([[2026-1029-weaviate-self-hosted-misma-base-de-datos-que-weaviate-cloud]]): **autoalojar convierte una línea de $/mes en una línea de RAM**, y esa línea de RAM ya está comprometida. Marcado para juicio humano, no auto-resuelto.

14. **Adoptar el motor no es una línea de código: es una decisión de versión, de API y de tres servicios que el self-hosted no tiene.** El corpus documenta seis vías de despliegue oficiales (Weaviate Cloud, Docker, Kubernetes, AWS, GCP Marketplace, DigitalOcean) de las que **solo Docker es applicable tal cual** al producto, que ya vive en nginx sobre VPS con un compose ([[2026-1029-weaviate-seis-vias-de-despliegue-y-cual-aplica-al-vps]]); además **la versión disponible difiere según la vía de despliegue**, y la **API GraphQL se apaga en Weaviate Cloud el 1 de mayo de 2027** —una fecha que ya es una deuda con calendario para cualquier cliente que quede en la nube ([[2026-1029-weaviate-graphql-deprecado-y-versiones-distintas-por-modo-de-despliegue]]).
