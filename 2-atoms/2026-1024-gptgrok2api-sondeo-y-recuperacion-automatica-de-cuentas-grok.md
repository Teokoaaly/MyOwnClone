## Claim
El sistema mantiene **sondas de salud automáticas** sobre las cuentas, con una regla de clasificación explícita de tres estados. Para Grok: la sondeo arranca **con el servicio**, corre **cada 60 minutos**, procesa **lotes de 50 cuentas**, y **solo sondea cuentas del pool con SSO guardado y no deshabilitadas**, reutilizando la interfaz de validación de cuota **sin enviar conversaciones** y **sin borrar ni deshabilitar cuentas automáticamente**. Solo si el runtime dice de forma explícita que la credencial está **inválida** se releen el correo y la contraseña guardados para **reloguear**; un resultado **"desconocido"** (timeout o error temporal) **solo se registra y se espera a la siguiente ronda**. El backoff de recuperación es **1 / 2 / 4 / 8 / 16 / 24 horas**, con máximo de 24 h. Para OAuth, la clasificación es por códigos explícitos (`invalid_grant`, `invalid_token`, `unauthorized_client`, o "la cuenta OAuth de CLI de xAI necesita reautorización"), y un **`402 personal-team-blocked` se considera cuota o permisos todavía no efectivos, no credencial inválida**: no se reautoriza, se reintenta a **60 / 120 / 300 segundos**. Los errores de TLS, proxy, red y los HTTP no clasificables **solo registran el fallo y conservan el estado de la cuenta**.

## Why It Matters
Es la pieza que convierte un repositorio de alta en **infraestructura operable**, y el contraste con el bot ya atomizado es directo: allí el bucle de reintento existe para **alcanzar una meta de cuentas creadas** ([[2026-1024-chatgpt-creator-worker-pool-y-retry-hasta-alcanzar-la-meta]]); aquí el reintento existe para **mantener viva una capacidad ya creada** — que es un problema distinto y mucho más caro. El valor de la regla de clasificación está en el punto que casi ningún proyecto del sector aplica: **la asimetría entre "inválido" y "desconocido"**. Un sistema que tratara un timeout como credencial muerta quemaría cuentas sanas en cada caída de red; este código decide explícitamente que un error de red **no deshabilita nada**.
Y la segunda regla, la del `402`, es aún más fina: **un error de pago o de propagación de cuota no es un error de autenticación**. Confundirlos produce la clasificación errónea de una cuenta sana, que es exactamente el error que un producto que depende de cuentas de suscripción no puede permitirse —y es el mismo tipo de fricción que el vault ya encontró en el lado del relay, donde "disponible" y "sirve el modelo que dice" son cosas distintas ([[2026-1024-gptgrok2api-compatibilidad-multiprotocolo-y-despacho-por-modelo]]).
Para MyOwnClone la lección transferible es de **operación de credenciales**: cualquier integración que dependa de cuentas o tokens de terceros —relays, gateways, cuentas de suscripción— necesita esta misma taxonomía de tres estados (inválido / desconocido / no efectivo por cuota) antes de tener un producto, porque **cada clasificación errónea destruye capacidad**. Y el backoff exponencial con tope de 24 h es la forma barata de implementarlo.

La captura **no** publica: cuántos sondeos fallidos se acumulan antes de una acción, ni si el estado "inválido" invalida permanentemente la cuenta, ni el coste en tiempo de CPU del sondeo continuo.
